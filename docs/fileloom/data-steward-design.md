# 数据管家设计文档

版本：v0.2
范围：Web 面板、文件域交互、产品文案与状态设计。
配套：[架构](data-steward-architecture.md)、[设计规范](data-steward-design-standards.md)、[优化计划](data-steward-optimization-plan.md)。

## 1. 产品判断

数据管家不是“把文件 API 做成页面”，而是一个用户每天愿意打开的本地文件产品。用户不关心索引、快照、哈希和操作 ID；用户关心三件事：

1. **我刚放进来/刚改过的文件，下次一打开就能看到。**
2. **我要整理文件时，清楚知道会移动什么、什么时候生效、怎么撤回。**
3. **我不想学一套复杂系统，打开就知道下一步点哪里。**

因此 v0.2 的核心调整是：把“最近/推荐”放到首页，把“整理”做成一个完整、可回退的流程，把技术概念藏在详情里，把导航收敛成三个主要入口。

### 1.1 设计原则

- **先看到，再操作**：默认打开首页；最近文件和待处理事项优先于系统状态。
- **结果可解释**：推荐卡片必须说明“为什么推荐”；整理方案必须展示移动前后的完整清单。
- **破坏性动作可撤回**：整理前自动备份；结果页立即提供撤销；撤销前检查冲突。
- **一次只问一件事**：用分步流程而不是一屏塞满按钮；弹窗只做当前这一件事。
- **技术细节渐进披露**：ID、哈希、索引范围默认收起，需要时在详情中查看。
- **界面用语面向结果**：用“更新文件清单”“预览整理方案”“撤销这次整理”，不用“scan/classify/rollback”。

## 2. 用户与任务

### 2.1 随手放文件的用户

行为：把文件拖进窗口，不关心落在哪个文件夹，甚至不记得文件名。
目标：下次打开能立刻看到；最好知道它还在不在、有没有被整理走。
设计回应：全局拖入默认进收件箱；所有上传写入持久收件记录；首页“最近文件”置顶；导航“整理”显示待整理数量；上传后立即更新索引，搜索即可找到。

### 2.2 想清理文件的用户

行为：积累了一批下载/截图/拍摄文件，想按规则归档。
目标：先看方案，再决定；做错了能恢复。
设计回应：三步骤流程（更新清单 → 预览方案 → 确认整理）；方案完整分页；执行前二次确认；结果页提供撤销。

### 2.3 谨慎的用户

行为：担心 AI/自动化误删或乱移文件。
目标：知道系统不会覆盖、不会跟随链接、不能永久删除。
设计回应：删除只进回收站；目标已存在即报冲突；撤销前检查被修改的文件；界面明确说明“整理前自动备份”。

## 3. 核心概念

| 用户看到的概念 | 实际含义 | 不应作为主文案的说法 |
|---|---|---|
| 收件箱 | 根目录下 `收件箱/`，随手放入文件的默认落点 | ingest、upload queue |
| 最近文件 | 通过上传/拖入进入系统、且仍存在的文件，按进入时间倒序 | ingest.json |
| 文件清单 | 最近一次扫描的索引，用于搜索与整理 | index、scanId |
| 整理方案 | 根据规则计算出的“将移动哪些文件、移到哪里”，尚未执行 | plan、planId |
| 整理记录 | 每次执行的移动结果，可查看、可撤销 | operation、rollback |
| 备份点 | 整理前或手动创建的文件级备份 | snapshot、hard link |
| 回收站 | 删除文件的暂存区，可恢复 | trash |

心智模型：

```text
放进来（收件箱/最近）
   → 看清楚（文件页）
   → 想好怎么放（整理方案）
   → 执行（整理记录）
   → 后悔（撤销/备份点）
```

## 4. 信息架构

### 4.1 为什么从 6 个 Tab 改成 3 + 更多

旧界面把“文件/概览/规则/快照/回收站/设置”平铺在一行，混用了：

- **地点**（文件）
- **任务**（整理）
- **历史**（快照/操作）
- **配置**（规则/设置）

用户不知道“扫描”和“整理”的关系，也不知道“快照”在哪一步产生。v0.2 按用户任务重组：

```text
首页    —— 我回来先看什么
文件    —— 我在哪里找文件
整理    —— 我要做一件有风险的事
更多 ▾  —— 整理记录 / 回收站 / 整理规则 / 设置
```

- “概览”被合并进“整理”的第一步，因为它只服务于整理决策。
- “快照”改名为“备份点”，放进“更多 → 整理记录”的第二个分段。
- “最近”不单独做 Tab，而是首页的第一等区块；避免用户还要多点一次。
- 设置和规则是低频项，放进“更多”，但仍可发现。

### 4.2 全局头部

从左到右：

1. 品牌标记 + “数据管家”。
2. 主导航：首页 / 文件 / 整理 / 更多。
3. 根目录切换（只有一个根时显示为只读胶囊）。
4. “问 AI”入口。

“整理”导航带待整理数量徽标；其他页面底部出现“N 个待整理”悬浮按钮，点击进入整理。

## 5. 首页

首页回答三个问题：**有没有新东西？有没有需要我处理的？上次看到哪了？**

### 5.1 区块顺序

1. **Hero + 收件箱拖放区**
   - 标题：“把文件放进来，剩下的交给我”。
   - 副文案：拖进这里进入收件箱；下次打开首页，最新文件排在最前。
   - 拖放区同时支持点击选择文件。
   - 信任说明：整理前自动备份，失败自动恢复。
2. **需要你处理**（推荐区）
   - 最多 3–4 张卡片，按优先级排列（见 5.3）。
   - 没有可推荐事项时，替换为三步引导（放入 → 预览方案 → 撤销）。
3. **最近文件**
   - 展示最近 8 个，可展开全部（最多 30）。
   - 每项：文件名、相对路径、进入时间、大小、是否已被索引。
   - 点击直接进入文件页并选中该文件。
4. **最近打开 / 最近整理**（两栏）
   - 最近打开来自浏览器本地记录，最多 12 条，展示 6 条。
   - 最近整理来自服务端操作记录，展示 3 条，可跳转记录页。

### 5.2 “下次一眼看到”的保证

“最近文件”不是按文件修改时间临时排序，而是来自持久化的 `ingest.json`：

- 上传成功即写入一条记录（路径、原文件名、时间、来源、大小、哈希）。
- 文件被整理/移动时同步改写记录中的路径。
- 文件被删除或移走后，读取时通过 `lstat` 过滤，不会展示幽灵条目。
- 客户端关闭、dsh 重启后仍存在。
- 上传同时更新索引，搜索立即可见，不需要用户再扫描。
- 首页默认作为登录后的第一个面板，最近文件位于首屏。

因此用户“随手拖进去、不看文件夹”，下次打开仍能在首页第一屏看到它，并且能点进所在目录。

### 5.3 推荐规则（可解释、本地、非模型）

推荐不是黑盒，全部来自本地状态：

| 卡片 | 触发条件 | 行动 |
|---|---|---|
| 收件箱有 N 个文件待整理 | `recent.pendingCount > 0` | 进入整理，范围自动设为收件箱 |
| 先更新文件清单 | 当前根没有索引 | 进入整理第一步 |
| 继续浏览“文件夹名” | 本地记录的上次浏览路径不是根目录 | 打开该目录 |
| 上次整理可以撤销 | 最近一条操作是 `succeeded` 且移动数 > 0 | 打开整理记录 |

不做的推荐：基于内容的 AI 推荐、跨根习惯推断、高频评分。这些既不可解释，也容易让用户误以为系统在“偷看内容”。

## 6. 上传与收件箱

### 6.1 入口

- **首页 Hero 拖放区**：始终上传到 `收件箱/`。
- **首页文件选择**：同上。
- **文件页拖放**：上传到当前文件夹。
- **文件页“上传”按钮**：上传到当前文件夹。
- **文件页侧栏“上传到当前文件夹”**：同上。

### 6.2 规则

1. 上传不覆盖：目标重名时自动生成 `name (1).ext`。
2. 文件名不能包含路径分隔符、控制字符或 Windows 保留设备名。
3. 单文件上限 512 MB；超过时明确报错。
4. 上传成功 → 写收件记录 → 更新索引 → 刷新首页/文件页 → toast 给出“已收进收件箱，可在首页最近文件看到”。
5. 上传失败 → 该文件单独报错，不阻塞队列中的其他文件。
6. 上传过程中按钮显示 busy 和进度，不允许重复触发。

### 6.3 为什么不做“自动整理上传文件”

自动整理会让文件“消失”到用户不熟悉的目录，违背“下次一眼看到”。v0.2 的默认是：**先收好，再让用户确认整理**。未来可以增加“上传后自动执行规则”的显式开关，但默认关闭。

## 7. 文件页

### 7.1 布局

```text
面包屑 + 搜索 + 上传 + 新建文件夹 + 刷新
┌──────────┬────────────────────────────┬──────────────┐
│ 文件夹    │ 文件表（名称/大小/时间/操作） │ 详情与预览    │
│ 当前层    │                            │ 元数据 + 操作  │
└──────────┴────────────────────────────┴──────────────┘
```

- 左侧只展示当前目录的子文件夹，不展示整棵树：足够导航，认知负担低。
- 双击文件夹进入；双击文件在右侧预览。
- 单击文件选中并记录“最近打开”。
- 搜索基于最近文件清单；新上传会自动进入索引。
- 搜索结果展示“所在位置”列，双击跳转到所在文件夹并选中文件。
- 表格支持按名称/大小/时间排序（文件夹始终在前）。
- 行操作收进“更多”菜单，避免每行四个文字按钮造成噪音。

### 7.2 单文件操作

| 操作 | 交互 | 安全约束 |
|---|---|---|
| 新建文件夹 | 弹窗输入名称，实时校验 | 目标存在即报错 |
| 重命名 | 弹窗预填原名 | 不覆盖；文件夹直接改名 |
| 移动 | 目标文件夹选择器 + 名称 | 不覆盖；目录可移动 |
| 复制 | 目标文件夹选择器 + 名称 | 仅支持普通文件；哈希校验 |
| 删除 | 确认弹窗，说明进入回收站 | 仅普通文件；不永久删除 |
| 下载 | 浏览器下载 | 通过预览路由读取 |

所有破坏性操作使用应用内弹窗，不使用 `window.confirm/prompt`；Esc 可关闭，焦点被限制在弹窗内。

### 7.3 预览

- 图片、视频、音频、PDF、文本内嵌预览。
- 文本最多展示 200 KB；非媒体内容预览上限 64 MB，音视频支持 HTTP Range 流式读取。
- 不支持的类型显示说明和下载入口，不显示空白。
- 读取失败显示可理解原因。

## 8. 整理页（核心操作逻辑）

整理页是唯一会批量移动文件的地方，必须让用户在任何时刻知道：“现在在哪一步、点了会发生什么、失败了会怎样”。

### 8.1 三步流程

```text
① 更新文件清单    只读；替代旧“扫描”
② 预览整理方案    只写计划；不移动文件
③ 确认并整理      先备份，再移动；失败自动恢复
        ↓
   结果卡片       立即提供“撤销这次整理”和“查看记录”
```

每一步都是独立卡片，带编号、标题、解释和唯一主按钮。

### 8.2 状态与可用性

| 状态 | 允许的动作 | 界面表现 |
|---|---|---|
| 无索引 | 更新文件清单 | 第一步高亮；第二步按钮禁用并解释原因 |
| 有索引但范围未覆盖 | 重新更新 | 显示范围警告，禁用生成方案 |
| 索引截断/有警告 | 仍可生成方案 | 显示黄色/红色提示，建议缩小范围 |
| 有方案、moveCount = 0 | 无需执行 | 显示“已经整理好了” |
| 方案过期/索引变化 | 重新生成 | 明确提示“方案已过期或清单已变化” |
| 执行中 | 禁止重复提交 | 按钮 busy；弹窗不可关闭 |
| 执行成功 | 查看记录 / 撤销 | 结果卡片常驻，直到离开页面 |
| 执行失败且已自动回滚 | 重新生成/重试 | 错误信息包含自动回滚结果 |

### 8.3 范围选择

- 默认“整个数据根”。
- 支持“收件箱”快捷入口（从首页推荐进入时自动选中）。
- 支持目录选择器。
- 如果索引只覆盖某个子目录，而用户选择其父目录，界面明确显示“清单只覆盖 X，请重新更新”。

### 8.4 方案预览

- 摘要四格：将移动 / 已在正确位置 / 未匹配 / 重名。
- 一句人话总结，避免只给数字。
- 显示规则来源（内置/我的）和方案有效期。
- 完整清单分页，每页 50 条；支持按文件名/目标筛选、按类型筛选。
- 每行展示：原位置 → 新位置、类型、大小；重名条目有标记。
- 执行按钮只在用户看到方案后出现，并且需要确认弹窗。

### 8.5 执行与撤销

- 确认弹窗文案说明：会改变位置、可撤销、备份点自动创建。
- 执行成功：结果卡片显示移动数量、操作 ID（次要信息）、撤销按钮。
- 撤销：再次确认；服务端先检查冲突；若目标被修改则整体拒绝，并显示原因。
- 失败：错误信息说明是否已自动回滚，不允许在状态不明时继续操作。

## 9. 整理记录与备份点

### 9.1 两个分段

- **整理记录**：按时间倒序列出操作；状态、移动数/总数、操作 ID；可查看详情，`succeeded` 可撤销。
- **备份点**：列出自动备份和手动备份；可查看涉及文件，可恢复。

### 9.2 操作详情

- 顶部元信息：状态、操作 ID、备份点 ID、时间、错误。
- 文件表：原位置、新位置、结果（未执行/已移动/已恢复/失败）。
- 超过 500 条只显示前 500 条并明确提示。

### 9.3 不可逆性保护

- `rolled_back` 的操作不再显示撤销按钮。
- 撤销失败时保留详情并显示冲突原因，不笼统报“失败”。
- 备份恢复说明“缺失文件补回；被修改的文件不覆盖”。

## 10. 回收站

- 列表：原位置、大小、删除时间、恢复。
- 恢复前确认；原位置被占用时提示冲突。
- 明确说明当前版本不提供永久删除，避免用户误以为文件已彻底删除。
- 空状态说明“删除的文件会先到这里”。

## 11. 整理规则

### 11.1 阅读模式

- 规则卡片：名称、分类、优先级、匹配条件、目标模板。
- 来源徽标：内置 / 我的。
- 规则文件路径和条数放在次要位置。
- “恢复内置规则”只在用户规则存在时出现。

### 11.2 编辑模式

- 默认仍是 JSON 高级编辑，但不再是一整块裸文本框：提供变量说明侧栏、实时校验、保存确认。
- 保存前明确提示“会完全替换当前规则，不会立即移动文件”。
- 解析失败时禁止保存并显示具体错误。
- 恢复内置规则需要二次确认。

### 11.3 为什么不先做可视化规则编辑器

规则包含扩展名、正则、大小区间、优先级和模板，可视化表单成本高且容易产生歧义。v0.2 先保证“看得懂、改得对、错了有提示”，后续再做表单化。

## 12. 设置

只读展示：

- 数据根列表和当前根。
- 单次扫描上限、方案有效期。
- 当前索引状态。
- 本地状态目录说明。
- 键盘快捷键。
- 产品版本与 AI 能力说明。

根目录通过 `DSH_DATA_STEWARD_ROOT` 配置，界面不提供写入，避免误改导致服务不可用。

## 13. 全局交互

### 13.1 弹窗

- 所有确认、输入、选择都使用应用内弹窗。
- Esc 关闭；点击遮罩关闭；Tab 焦点循环；关闭后焦点回到触发元素。
- 主操作在右，取消在左；危险操作用红色按钮。
- 执行中的弹窗不允许关闭。

### 13.2 反馈

- 加载：局部 Spinner，不遮挡整个页面。
- 成功：toast（5 秒）+ 结果卡片/列表变化。
- 错误：页面内错误条 + 重试；不吞错。
- 空：解释为什么空 + 一个明确动作。
- 禁用：按钮禁用并给出原因（文案或提示），不静默。

### 13.3 键盘

- `Ctrl/Cmd + K`：聚焦文件页搜索。
- `Esc`：关闭弹窗/菜单。
- `Enter`：提交当前输入或执行搜索。
- 所有可点击元素都有可见 focus 样式。

### 13.4 可访问性

- 弹窗 `role="dialog"`、`aria-modal`、焦点限制。
- Toast 使用 `aria-live="polite"`。
- 图标按钮必须有 `aria-label`。
- 正文最小 13px，辅助信息最小 12px；对比度依赖 DSH 语义 token 与本地混合状态色。
- 不依赖颜色单独传达状态；状态同时有文字。

## 14. 文案与国际化

- 所有用户可见文案进 `locales.ts`，支持中英两套；不在组件里散落中文（预览错误等已收敛）。
- 动作文案以动词开头：“更新文件清单”“生成整理方案”“开始整理”“撤销这次整理”。
- 错误文案回答三件事：发生了什么、文件是否安全、下一步怎么做。
- 技术 ID 不作为主信息；只在详情/复制场景出现。
- 空状态给出下一步，不写“暂无数据”。

## 15. 边界场景

| 场景 | 设计 |
|---|---|
| 上传重名 | 自动 `(1)`，不覆盖，toast 显示最终路径 |
| 上传失败 | 单文件失败不影响其他；显示失败数量 |
| 索引未建立就搜索 | 明确提示先更新清单 |
| 索引只覆盖子目录 | 整理时警告并禁用执行 |
| 方案过期 | 提示重新生成，不自动执行 |
| 执行中源文件被改动 | 服务端预检拒绝，界面显示原因 |
| 撤销时目标被修改 | 整体拒绝，不覆盖用户修改 |
| 删除文件夹 | 当前版本禁用并说明 |
| 回收站原路径被占用 | 恢复报冲突，保留原文件 |
| 无数据根 | 说明环境变量配置方式，不展示空壳界面 |
| 浏览器禁用 localStorage | 最近打开/上次路径失效，但最近文件与所有文件操作仍可用 |

## 16. 明确不做

- 不做自动整理上传文件（默认）。
- 不做基于模型内容的推荐/搜索。
- 不做永久删除、文件夹删除、批量多选。
- 不做真实 NAS、原生快照、EXIF/TMDB。
- 不做深链接/多标签路由。

这些放入后续版本，避免界面再次变成“功能清单”。
